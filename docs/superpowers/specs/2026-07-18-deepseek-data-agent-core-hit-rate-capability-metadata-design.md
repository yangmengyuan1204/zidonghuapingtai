# DeepSeek 数据智能体核心命中率与脚本能力元数据设计

## 1. 背景与现状

本次升级分为两个阶段：先稳定现有日本站核心流程的自然语言首次命中率，再建立脚本能力元数据，逐步让智能体覆盖全部数据脚本。

现有智能体采用“DeepSeek 结构化候选 + 后端确定性纠偏 + 合同归一化 + 工具执行 + 真实状态校验”的混合结构。历史分析记录显示，38 次识别中有 18 次出现 DeepSeek 已返回 `ready`，但后端合同归一化仍将会话打回澄清。这说明当前主要问题不是模型本身，而是意图规则、默认值、合同编译和脚本事实之间不一致。

当前工作区存在大量未提交改动。后续实施必须将其全部视为用户现有成果，只修改本需求涉及的文件，不回退、不覆盖、不提交无关改动。

## 2. 目标与非目标

### 2.1 第一阶段目标

- 覆盖完整日本站标准链路：购物车、订单提出/翻译/确认/报价/支付、采购、上架、配送单提出/报价/支付，以及已有订单/配送单续跑和问题产品。
- 明确信息的指令首次生成正确可确认合同的命中率不低于 95%。
- 业务上确有歧义的指令准确指出缺失项，不产生无关追问。
- 所有默认值、推断值、模型纠偏和权限切换可审计。
- DeepSeek 波动或解析失败时，确定性规则仍能尽量生成安全合同。

### 2.2 第二阶段目标

- 为现有数据脚本建立统一能力元数据。
- 智能体按当前项目、业务模块、风险等级和启用状态发现能力。
- 新脚本接入不再要求同时修改主服务、Prompt、工具目录和多处正则。

### 2.3 非目标

- 第一阶段不重写数据脚本业务代码，不改变脚本公共函数签名、入参或返回值。
- 不新增数据库表或字段。
- 不允许自然语言绕过合同确认、账号权限或高风险确认。
- 不在第一阶段一次性接入全部 25 类脚本。

## 3. 总体架构

保留现有“目标分析 → 用户确认 → 后台执行 → 真实结果校验”主流程，重新划分内部职责：

- `data_factory_agent.py`：会话、确认、执行编排、暂停和恢复。
- `data_factory_agent_intent.py`：从用户原文提取确定性字段与证据。
- 独立合同编译模块：合并字段、应用默认值、识别歧义、生成最终合同。
- `data_factory_agent_prompts.py`：要求 DeepSeek 产生语义候选与证据，不决定最终业务合同。
- `data_factory_agent_tools.py`：执行确认后的合同，处理支付降级与权限恢复。
- 数据脚本：继续作为业务执行与实际状态查询的事实来源。

核心数据流：

```text
自然语言 + 顶部客户ID + 环境账号
  → 确定性字段提取
  → DeepSeek语义候选
  → 合同字段合并与默认补全
  → 歧义/冲突/风险校验
  → 可确认合同
  → 工具执行
  → 真实接口状态校验
```

## 4. 意图状态与合同编译

### 4.1 字段来源优先级

合同字段按以下优先级合并：

1. 用户最新一轮明确修订。
2. 用户此前已明确且未被修改的字段。
3. DeepSeek 有用户原文证据支持的语义候选。
4. 页面与环境上下文。
5. 业务默认值。

每个字段记录规范化值、用户原文证据、消息轮次、来源和是否为自动推断。模型候选不能覆盖用户明确值，也不能凭空注入订单号、客户 ID 或业务操作。

### 4.2 新建订单默认合同

用户未明确说明时使用以下默认值，并在确认界面醒目标注：

- 目标节点：订单待付款 `order_offered`。
- 店铺数：1。
- 每店商品种类数：1。
- 每种购买数量：1。
- 商品关键词：衣服。
- 店铺类型：`1688`。
- 价格：统一单价 10 元。
- 支付策略：余额优先，余额不足时自动切换银行支付。

### 4.3 已有订单与配送单

- 用户只要求改价、问题产品、退款等后置操作时，不要求目标节点，也不推进订单状态。
- 商品种类数、原数量和原单价从订单查询接口读取，不要求用户重复提供。
- 用户明确要求推进状态时，才生成对应推进操作。
- 订单号包含客户 ID 后缀时，将其作为事实来源进行一致性校验。

### 4.4 问题产品规则

- “第 N 番”只处理指定商品。
- “全部商品、每番、分别处理、两番都处理”等明确表达映射全部商品。
- 多商品但未说明处理范围时必须追问。
- 已明确处理范围但未说明修改项或目标值时必须追问。
- “全部退、全退了”表示剩余商品数量全部退、国内运费全部退、单价保持原值。
- “单价改成 0”等明确表达直接进入合同，不再追问商品种类数和原数量。
- 多操作按用户原话顺序写入合同，任何已知操作不得静默忽略。

### 4.5 允许澄清的情况

只有以下情况允许阻止合同确认：

- 问题产品范围或修改值确实缺失。
- 同一轮存在互相冲突的客户、数量、价格、节点或操作。
- 请求超出当前已启用能力。
- 权限、金额或批量范围需要人工确认。

普通缺省参数不允许触发澄清。澄清达到上限后保留状态并列出仍缺字段，不得强行生成可能错误的合同。

## 5. 客户上下文

### 5.1 来源优先级

客户 ID 优先级固定为：

1. 自然语言明确客户 ID。
2. 数据脚本页面顶部栏输入的客户 ID。
3. 当前环境或项目绑定测试账号对应的客户 ID。

顶部客户 ID 必须随创建会话请求传给后端，不能只保存在浏览器本地。合同展示客户 ID 及其来源。

### 5.2 一致性与安全

- 自然语言客户 ID 与订单号后缀冲突时停止并提示。
- 顶部客户 ID 与订单号冲突时，已有订单以订单事实为准并提示冲突。
- 模型返回但用户原文、页面和订单事实均无证据的客户 ID 必须丢弃。

## 6. 支付降级

- 初始支付方式为余额支付。
- 只有业务接口明确返回余额不足时，才允许切换银行支付。
- 认证失败、网络异常、业务校验失败等不能被归类为余额不足。
- 切换银行支付后自动完成银行流水和后台财务确认，不再中途二次确认。
- 合同、执行事件和最终结果记录支付切换原因，但不得记录敏感账号信息。

## 7. 问题产品 500 元权限恢复

### 7.1 自动切换

退款预览达到 500 元或接口返回部长权限限制时：

1. 保存当前操作序号、问题产品 ID、恢复阶段和已完成结果。
2. 根据当前项目和问题产品模块查找启用的“后台沈文妮账号”档案。
3. 自动注入该账号和 `allow_large_refund=true`，从暂停节点重试一次。
4. 已经创建或处理完成的问题产品步骤不得重复执行。

现有智能体账号恢复链路只保存账号档案 ID，没有设置 `allow_large_refund=true`；实施时必须修复这一缺口。

### 7.2 人工恢复

沈文妮账号缺失、不可用，或自动重试后仍返回相同权限限制时，会话进入 `awaiting_permission`。原智能体界面显示：

- 当前项目和当前脚本模块可用的测试账号档案下拉框。
- 临时后台账号输入框。
- 临时密码输入框。

用户可以选择账号档案，或提供临时凭据。提交后从暂停节点继续原任务。

### 7.3 敏感信息处理

- 临时密码不写入数据库、执行记录、分析记录、日志或 API 响应。
- 临时凭据只进入服务器进程内的短期敏感上下文。
- 任务成功、失败、取消、超时或会话清理时立即删除。
- 账号切换事件只记录档案 ID、档案名称或“临时账号”，不记录用户名和密码。

## 8. 模型与异常处理

- DeepSeek 负责语义候选，不拥有最终合同决策权。
- DeepSeek 超时、非法 JSON 或缺少字段时，优先用确定性字段和默认值编译合同。
- 确定性结果不足以安全判断时，返回准确错误或澄清问题。
- 后端不得将模型已正确识别的内容因旧约束再次打回无关澄清。
- 每次分析记录模型候选、最终合同、自动纠偏、字段证据、默认值和待确认项。
- 不支持能力必须记录为能力缺口，不能藏入摘要或 assumptions。

## 9. 评测与验收

### 9.1 离线测试

- 将现有真实失败记录脱敏后转换为固定回归语料。
- 覆盖全部标准流程节点、同义表达、数量、价格、客户、支付、续跑和问题产品组合。
- 合同编译器使用参数化测试，保证相同输入生成稳定合同。
- 覆盖顶部客户 ID 优先级、订单客户冲突、余额不足转银行、500 元自动换账号、人工续跑和敏感信息清理。
- 当前智能体相关测试与数据脚本合同测试必须全部通过，包括目前的 7 个回归失败。

### 9.2 真实 DeepSeek 评测

- 至少 60 条明确信息指令和 20 条歧义、冲突或不支持指令。
- 每条连续运行 3 轮，仅生成合同，不调用业务接口。
- 明确信息指令每轮首次正确可确认率均不低于 95%。
- 歧义指令必须准确指出真正缺失项。
- 同一指令三轮生成的关键合同字段保持一致。
- 评测汇总命中率与失败分类，不记录敏感数据。

### 9.3 低风险真实执行

- 评测通过后验证少量订单创建、余额不足转银行、已有订单问题产品和权限恢复。
- 使用低金额测试数据。
- 500 元权限链路优先使用受控模拟验证，避免为了测试制造不必要的大额退款。

## 10. 第二阶段脚本能力元数据

在不改变脚本公共函数签名的前提下，为每个脚本注册以下元数据：

- 脚本键、中文名称、业务模块和适用项目。
- 自然语言意图、同义表达、正反示例。
- 必填参数、可选参数、默认值、数据类型和来源优先级。
- 只读/写入属性、风险等级和确认策略。
- 所需账号类型、权限角色和账号筛选范围。
- 前置状态、目标状态、恢复节点和幂等要求。
- 执行函数、结果校验器和智能体启用状态。

智能体只加载当前项目、当前模块且已启用的能力。元数据先存放在代码中进行版本管理，不新增数据库结构。

接入顺序：

1. 只读查询和低风险能力。
2. 仓库、辅料等中风险能力。
3. 资金类能力，增加二次风险确认。
4. OEM 与批量能力，增加更严格的范围和账号校验。

## 12. 实施顺序

1. 修复当前 7 个测试回归并建立命中率基线。
2. 完成确定性意图与合同编译。
3. 接通顶部客户 ID 和默认账号来源。
4. 完成支付降级和 500 元权限恢复。
5. 运行离线语料、真实 DeepSeek 三轮评测和低风险执行。
6. 第一阶段验收后，开始脚本能力元数据建设。

## 13. 验收标准

- 明确信息指令首次正确可确认率不低于 95%。
- 默认值均在确认合同中醒目标注。
- 真正歧义准确追问，普通缺省参数不追问。
- 自然语言、顶部栏和环境账号的客户优先级正确。
- 余额不足自动切换银行并完成财务确认。
- 500 元限制自动尝试沈文妮账号，失败后可在原界面人工提供账号并继续。
- 已完成业务步骤不会因恢复执行而重复。
- 临时凭据不持久化、不出现在日志或响应中。
- 第一阶段不改变现有数据脚本公共契约。
- 自动化测试、真实模型三轮评测和低风险执行全部通过后才算完成。
