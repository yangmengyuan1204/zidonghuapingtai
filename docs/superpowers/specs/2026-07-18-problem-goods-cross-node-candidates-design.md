# 日本站问题产品跨节点候选查询设计

## 背景

“日本站问题产品处理”当前只通过 `/purchase.purchaseList` 查询可创建的问题产品候选。采购记录进入核查等后续节点后会离开该列表，导致订单仍有可提出数量，但页面显示没有可创建的新问题产品。

订单 `2026071816165891-300001` 可稳定复现：采购列表返回空，而 `/order.detail` 的四个订单明细均包含采购记录，状态为“核查中”，`possible_num=1`、`storage_num=0`。

## 目标

- 不使用固定节点白名单，以后台当前订单数据判断是否存在候选。
- 支持采购记录在不同业务列表之间流转后的查询。
- 保持现有问题产品创建、处理、权限和退款流程不变。
- 查询过程只读，最终是否允许创建仍以 `/problem.store` 的业务校验为准。

## 非目标

- 不修改问题产品处理状态机。
- 不修改数据库、项目配置或接口路径配置。
- 不调整其他数据脚本及前端交互。
- 不绕过后台对问题产品创建的业务限制。

## 方案

### 主数据源

以 `/order.detail` 作为候选采购记录的主数据源。读取 `data.order_detail[].order_purchase[]`，将订单详情和采购记录合并为统一候选结构。

订单详情跨采购、核查和后续节点保留订单明细与采购关系，因此候选查询不再依赖记录当前所在的业务列表。

### 兜底数据源

订单详情未返回采购记录或查询失败时，继续查询现有 `/purchase.purchaseList`，并补查 `/follow.followList` 的全状态数据。任一来源成功即可继续；所有来源均失败时才返回查询错误。

### 归一化与去重

所有来源转换为现有候选字段：

- `order_purchase_id`
- `order_detail_id`
- `sorting`
- `purchase_no`
- `possible_num`
- `storage_num`
- `max_submit_num`
- `can_submit`
- 价格、运费、确认数量和 OPTION

按 `order_purchase_id` 去重，主数据源优先；缺失字段可由兜底来源补齐。

`max_submit_num` 保持现有规则：`max(0, possible_num - storage_num)`。结果小于等于零时不可创建。

### 已有问题产品

继续查询已有问题产品。采购记录存在状态 1–4 的处理中问题产品时，禁止重复创建；已完成或已取消记录不阻止后台根据剩余数量再次判断。

### 最终业务校验

候选查询只负责展示后台当前订单数据，不模拟全部创建规则。用户提交后仍由 `/problem.store` 最终判断；后台拒绝时保留并展示原始业务原因，不自动换节点或重复提交。

## 修改范围

- `app/data_scripts/problem_goods.py`
  - 增加订单详情候选查询与解析。
  - 增加采购列表、核查列表兜底和去重。
  - 保持对外返回字段兼容。
- `tests/test_problem_goods_script.py`
  - 增加跨节点候选、来源兜底、去重和失败处理测试。

## 异常处理

- 主数据源失败：记录诊断信息并尝试兜底来源。
- 单个兜底来源失败：不影响其他成功来源。
- 所有来源失败：返回明确的候选查询错误。
- 查询成功但无采购记录：返回空候选，不误报接口故障。
- 字段缺失或无效：跳过无法标识采购记录的数据，避免生成不可执行候选。

## 验收标准

- 订单 `2026071816165891-300001` 返回四条候选，采购记录 ID 为 `15328208` 至 `15328211`。
- 四条候选的 `max_submit_num` 均为 1，且可选择创建。
- 同一采购记录被多个来源返回时只展示一次。
- 存在处理中问题产品的采购记录不可重复创建。
- `possible_num <= storage_num` 的采购记录不可创建。
- 主数据源不可用时能通过兜底来源返回候选。
- 所有来源失败时返回明确错误，不进行任何写操作。
- 现有问题产品处理测试继续通过。
