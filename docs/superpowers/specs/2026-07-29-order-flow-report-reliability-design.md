# 订单续跑与执行报告可靠性修复设计

## 背景

当前故障由四类独立问题叠加造成：

1. 订单确认请求在 `confirm_freight` 缺省时省略字段，后台仍强制读取该字段。
2. 内置订单流程固定使用 `Y001`，无法查询其他后台账号数据范围内的真实订单。
3. `/order.submitTranslate` 属于有副作用请求，读取响应超时后代码直接重试并判失败，未核对订单实际状态。
4. 报告列表依赖 `test_record` 数据库行；项目删除会删除记录，但 Allure 文件仍保留。新支付回归还把部分余额流水方向识别错误。

## 目标

- 所有订单确认请求始终包含合法的运费字段。
- 订单续跑、完整流程和支付回归统一支持项目后台账号档案，不再依赖固定账号。
- 翻译请求发生超时后，通过订单详情状态确认操作是否已经成功，避免重复写入和假失败。
- 失败报告准确标记实际失败节点。
- 项目删除不再静默删除执行记录；现存孤立 Allure 报告可恢复为可查询的历史记录。
- 支付回归按照业务流水语义判断余额收支方向，避免金额一致但方向标签映射错误。

## 方案

### 1. 后台账号解析

在数据脚本路由中复用现有测试账号档案解密能力，将档案中的账号、密码和验证码转换为 `backend_*` 运行变量。完整流程、订单续跑和支付回归共用一个小型解析函数。前端移除内置流程中的固定 `Y001`，允许显式选择后台账号档案；未选择时保留现有变量兜底，避免破坏已有自定义脚本。

### 2. 翻译超时对账

保持普通后台请求的现有重试行为，但对 `/order.submitTranslate` 使用单独的“写入后核对”流程：

1. 发起一次翻译请求。
2. 若明确返回业务失败，直接失败。
3. 若连接或读取超时，轮询订单详情。
4. 订单状态已经越过待翻译节点则按成功继续；仍在待翻译状态才允许受控重试。
5. 最终仍无法判断时返回“状态未知”，不伪装成明确业务失败。

报告在进入每个节点前记录当前节点，异常时使用该节点生成失败摘要。

### 3. 报告保护与恢复

项目删除接口在存在执行记录时拒绝直接删除，并返回记录数量及明确提示。暂不修改数据库结构，不做软删除迁移。

新增管理员恢复接口，扫描 `app/reports/allure-results/*-result.json`，仅为数据库中不存在的文件建立最小 `test_record` 索引。恢复过程必须幂等，不覆盖已有记录，不删除文件；无法解析的文件计入跳过数量。

### 4. 支付流水方向

支付回归校验以流水类型、金额符号和业务引用共同归一化收支方向，不直接把接口展示标签当作最终方向。余额支付应判定为客户余额扣减；银行支付继续使用财务确认账单。缺少可验证证据时标记阻塞，不将不确定结果判为通过。

## 预计文件

- `app/data_scripts/order_support.py`：运费字段、翻译超时对账、节点错误信息。
- `app/routers/data_scripts.py`：统一后台账号档案解析。
- `static/full-flow.js`：账号档案选择与固定账号移除。
- `app/routers/projects.py`：项目删除前的报告保护。
- `app/routers/test_records.py`：孤立报告恢复接口。
- `app/data_scripts/payment_amount_regression/`：支付流水方向归一化。
- `tests/` 下对应定点测试：覆盖上述行为。

这些文件部分已有未提交改动。实施时只追加本设计相关修改，不覆盖或回退现有工作。

## 验收标准

- 缺少运费输入时，确认请求仍包含 `confirm_freight` 和 `confirm_dicker_freight`。
- 选择后台账号档案后，订单续跑使用档案账号；没有静默回落到 `Y001`。
- 翻译响应超时但订单状态随后变为已翻译时，执行结果不判失败且不重复提交。
- 真正未翻译或状态未知时，报告包含准确节点和明确原因。
- 有执行记录的项目无法直接删除。
- 历史报告恢复连续执行两次不会产生重复记录。
- 支付回归中的余额支付方向和金额核对正确，证据不足时保持阻塞。
- 本次定点测试和相关既有测试全部通过。

## 非目标

- 不恢复已丢失且没有 Allure 文件的完整日志。
- 不修改远端业务系统权限或订单归属。
- 不修改数据库文件、环境配置、密钥和启动脚本。
- 不重构无关的数据脚本、前端 V2 或系统回归模块。
