# 日本站系统回归真实执行修复设计

## 目标

修复日本站系统回归真实执行中已经复现的四类问题：分批付款尾款取证失败、配送单人民币金额被当作日元、配送单银行支付长时间占用、问题产品前置订单无法提出问题产品；同时恢复服务重启后遗留的 `running` 状态。

## 设计

### 支付证据

- 分批付款尾款预期值只接受支付响应或预览数据。优先读取 `order_tail_payment.pay_amount`、`data.pay_amount` 和嵌套 `pay_data`，禁止把请求字段作为实际流水。
- 配送单详情中的 `pay_amount` 是人民币，`exchange_rate` 是人民币兑日元汇率，`pay_amount_jpy` 是接口给出的日元结果。回归预期证据保存人民币原值和汇率，通过统一 Decimal 算法换算日元，并与接口日元字段交叉校验。
- 配送单付款脚本仍提交后端要求的人民币 `pay_amount`，只修正回归对账证据的币种含义。

### 执行时限

- 系统回归调用配送单银行支付时提供独立的保守默认值：单次请求 8 秒、财务查询 2 轮、轮询间隔 1 秒。
- 用户明确填写的超时或重试参数优先，避免改变已有数据脚本的默认契约。
- 达到边界后返回 `blocked` 和具体阶段，不把支付请求参数当作实际金额，也不自动重放状态不明的写请求。

### 问题产品前置单

- 前置订单停在 `checking_started`：后端此时已经生成可核查采购记录但尚未上架，满足源码要求的 `possible_num - storage_num > 0`。真实验证表明 `purchase_paid` 尚不会出现在问题产品候选接口中。
- 若完整流程已经创建订单但在翻译/报价阶段返回状态竞争错误，使用返回的订单号调用恢复流程，不重新创建同一用例订单。
- 候选为空时记录采购候选数量、`possible_num`、`storage_num` 和 `can_submit`，便于区分数据不足与流程节点错误。

### 中断恢复

- FastAPI lifespan 初始化数据库后调用现有 `reconcile_interrupted_runs()`。
- 所有遗留 `running` 用例转换为 `blocked / unknown_write_state`；不自动重跑可能已经写入支付或问题产品数据的步骤。

## 验证标准

- 分批余额和银行场景都能取得首款、尾款，并验证两者合计等于订单报价。
- 配送单 775.02 CNY、汇率 21.10 的预期结果为 16353 JPY，与客户余额或已确认银行流水一致。
- 配送单银行异常请求在设定边界内结束并给出明确状态。
- 问题产品首条场景能够取得 `can_submit=true` 的采购明细并进入问题产品处理。
- 服务重启后不存在遗留 `running` 用例。
