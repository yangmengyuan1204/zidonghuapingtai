# 日本站系统回归拦截规则与费用证据设计

## 背景

日本站“系统回归”当前包含 77 条目录用例。支付与非拦截问题产品用例已能真实执行，但仍有两个可信度缺口：

- 15 条问题产品拦截用例只声明了 `guard_kind`，实际仍统一调用普通问题产品流程，没有构造规则要求的业务状态。
- `JP-PAY-009` 和 `JP-PAY-010` 只声明了费用组合名称，现有执行器没有保证固定金额 OPTION、百分比 OPTION 和全部费用真实进入订单，也没有保存分项证据。

本次目标是消除这两类“目录声明与真实执行不一致”，使每条用例可以独立填写参数、单独或批量执行，并以真实接口和真实业务证据判定结果。

## 范围

### 包含

- 日本站 15 条问题产品拦截用例的规则级执行。
- 各拦截用例独立的前置状态、动作、预期错误和无副作用证据。
- `JP-PAY-009` 多 OPTION 混合订单的真实费用构造与分项断言。
- `JP-PAY-010` 全费用混合订单的真实费用构造与分项断言。
- 单选、全选和任意多选沿用现有系统回归批次入口。
- 每条用例继续使用普通输入框、数字框、选择框和 OPTION 行编辑器，不要求用户输入 JSON。

### 不包含

- 修改业务后端 PHP 源码。
- 新增数据库字段或表。
- 修改其他数据工厂脚本的接口契约。
- 用前端校验、平台本地模拟或请求参数代替真实后端拦截与真实费用证据。

## 方案选择

采用“规则分阶段执行”方案。每条拦截规则声明自己的前置状态构造器和目标动作，执行器按规则调用提出、业务决策、采购处理、OPTION 计算或配货直完入口。

不采用以下方案：

- 本地模拟后端错误：不能证明真实接口仍有校验。
- 继续使用统一普通流程：无法稳定触发不同阶段的规则。
- 仅保留人工测试：不满足一键自动回归目标。

## 模块边界

### `guard_scenarios.py`

新增日本站规则目录，负责声明而不执行：

- `guard_kind`
- 规则所属业务阶段
- 默认可编辑参数
- 前置状态要求
- 目标动作
- 预期错误关键字
- 禁止出现的业务写入或状态跃迁

该文件不包含 HTTP、登录和金额计算。

### `guard_executor.py`

新增规则执行服务，负责：

1. 创建或定位独立订单。
2. 构造该规则要求的业务状态。
3. 保存动作前证据。
4. 仅执行一次目标动作。
5. 捕获真实后端响应。
6. 保存动作后证据并检查结构化业务变化。

普通拦截规则只执行一次目标动作。`large_refund_account` 是例外的复合场景，必须先由普通账号验证权限拦截，再由部长账号从同一问题产品、同一阶段继续执行。

规则执行返回统一载荷：

```text
execution_id
batch_id
case_id
status
reason_code
guard_kind
expected_stage
actual_stage
actor
order_sn
problem_goods_id
purchase_record_ids
parameter_snapshot
precondition_evidence
attempted_actions
response_evidence
before_evidence
after_evidence
required_effects
forbidden_effects
allowed_effects
unclassified_effects
business_diffs
failure_reason
```

### `guard_runner.py`

保留为纯判定器：

- 环境缺少构造前置状态所需能力：`blocked / precondition_capability_missing`。
- 无法调用目标提交接口：`blocked / target_action_unavailable`。
- 命中声明的真实后端错误且无禁止副作用：`passed`。
- 接口成功或错误不匹配：`failed / guard_not_triggered`。
- 命中其他错误：`failed / unexpected_guard_error`。
- 动作结果无法确认：`blocked / unknown_write_state`，禁止自动重放。
- 已成功调用目标接口但后端没有对应服务端校验：`failed / backend_guard_missing`，不得用前端限制冒充通过。

对错误的匹配顺序固定为：业务错误码或结构化错误字段、HTTP 状态、错误文案正则。判定时必须同时满足 `actual_stage == expected_stage`；前置构造阶段提前出现相同文案不能通过。

结果 `status` 只使用 `passed`、`failed`、`blocked`、`waiting`。`unknown_write_state`、`backend_guard_missing`、`account_required` 等均只作为 `reason_code`。批次编排内部仍可使用 `pending` 和 `running` 表示尚未产生用例结果的瞬时状态。

### `payment_runner.py`

扩展费用组合参数翻译与结果断言：

- 把 `option_profile=fixed_and_rate` 转换为订单实际可选的一个固定金额 OPTION 和一个百分比 OPTION。
- 把 `fee_profile=all` 转换为商品金额、每番国内运费、其他费用名义与金额、固定 OPTION、百分比 OPTION。
- OPTION 必须通过 `option_id` 唯一识别；名称只用于展示和辅助诊断。
- 从报价详情和订单详情读取分项证据，不使用请求参数作为已生效证据。
- 任一必需分项缺失时返回 `failed / fee_component_missing`，即使支付总额对账通过也不能通过。

## 前置状态原则

- 每条用例使用独立订单和批次备注，不复用同一问题产品。
- 优先通过现有数据脚本公开能力创建状态，不直接改数据库。
- 只有接口真实返回和随后查询到的状态可作为前置证据。
- 如果环境无法创建转寄订单、多采购或配货直完所需状态，用例返回 `blocked / precondition_capability_missing` 并说明缺失能力。
- 候选不可见、`can_submit=false` 或页面按钮不可用只作为辅助证据；必须调用真实目标接口。无法调用时返回 `blocked / target_action_unavailable`。
- 写请求遇到超时或网络中断时必须查询业务状态并归类为 `confirmed_written`、`confirmed_not_written` 或 `indeterminate`。
- `confirmed_written` 继续结果验证；`confirmed_not_written` 只有在动作声明为可安全重试时才允许重试；`indeterminate` 返回 `blocked / unknown_write_state`，禁止自动重试。

## 大额退款账号策略

- 退款预览达到或超过 500 元时，普通账号先执行真实采购处理，必须保留权限错误、动作前后问题产品状态和余额账单差集；存在退款或余额变化时第一步失败。
- 第一步通过后，使用项目内默认的沈文妮部长账号从相同问题产品、相同采购处理阶段继续。
- 自动登录失败时用例进入 `waiting / account_required`，页面显示账号和密码输入框；用户提交后从相同问题产品和相同阶段继续，不重新造单。
- 部长步骤完成后轮询客户账单，验证退款方向、金额、唯一业务关联和最终问题产品状态。
- 退款实际入账只查询客户余额账单，不设计银行退款渠道。

## 执行状态持久化与恢复

- 创建用例执行记录时生成不可变 `execution_id`，并把目录参数、页面参数和批次变量合并成该执行独立的 `parameter_snapshot`。页面后续修改不影响已创建执行。
- 复用 `SystemRegressionCaseRun.snapshot_json`、`resume_stage`、订单号和问题产品 ID 字段，并在 `result_json` 中持久化采购记录 ID、当前步骤、动作前证据、已完成动作和结构化业务差异；不新增数据库字段。
- 每个有写入风险的阶段在请求前先持久化 checkpoint，请求后再持久化响应和查询证据。
- `waiting / account_required` 在服务重启后保持等待状态。恢复账号只继续部长步骤，不重新造单、不重做普通账号拦截步骤。
- 服务重启时发现 `running`：根据最后 checkpoint 查询真实业务状态。能确认写入则继续验证，能确认未写入则按动作重试策略处理，无法确认则转为 `blocked / unknown_write_state`。
- 恢复逻辑按 `execution_id`、订单号、问题产品 ID、采购记录 ID 和批次号查询，禁止误命中历史订单或其他批次数据。

## 结构化副作用模型

- `required_effects`：场景成功必须出现的业务变化。
- `forbidden_effects`：拦截步骤绝不能出现的退款、扣款、状态跃迁或新增业务记录。
- `allowed_effects`：允许但不决定通过的审计日志、访问时间等变化。
- `unclassified_effects`：无法归类的变化；非空时场景不能通过。
- `business_diffs`：按实体、字段、前值、后值和业务分类保存的差异列表。

`updated_at`、普通操作日志和查询痕迹默认不算业务副作用，但必须通过允许列表明确过滤，不能悄悄丢弃。

## 费用组成证据

`JP-PAY-009` 至少保存：

- 固定金额 OPTION：名称、计价类型、单价、数量、人民币小计。
- 百分比 OPTION：名称、计价类型、费率、计费商品金额、数量、人民币小计。
- OPTION 人民币合计与换算后的日元金额。

`JP-PAY-010` 至少保存：

- 商品金额。
- 每个番号的中国国内运费及合计。
- 其他费用名义和金额。
- 固定金额 OPTION。
- 百分比 OPTION。
- 报价人民币总额、证据汇率、报价日元总额和实际支付日元。

分项证据来自报价或订单详情。支付请求金额只可记录为请求上下文，不能证明分项已进入报价。

### 费用计算规则

- 固定金额 OPTION：`option_amount_cny = option_unit_price_cny × option_quantity`。
- 百分比 OPTION 按当前 `ProblemGoodsService::optionChangeDetail` 口径：`option_amount_cny = option_rate / 100 × option_quantity × goods_unit_price_cny`；商品数量不额外参与，OPTION 数量已经是乘数。
- 每个人民币分项使用 `Decimal` 计算并按 `ROUND_HALF_UP` 保留 2 位；不得使用二进制浮点数。
- 商品、每番国内运费、其他费用和 OPTION 先以人民币精确求和，再对人民币总额按报价证据中的汇率换算日元；不对每个分项分别取整。
- 日元总额使用 `ROUND_HALF_UP` 四舍五入到整数。
- 预期金额只使用该订单报价证据的汇率；支付响应中的汇率只能作为交叉核验，出现不一致时失败。
- 预期与实际支付相差不超过 1 日元通过，达到 2 日元失败。

### 费用组件集合

- `required_components`：场景声明必须存在且唯一匹配的分项。
- `optional_components`：允许存在但不影响本场景目标的分项。
- `forbidden_components`：场景声明不得出现的分项。
- `system_generated_components`：后端自动生成且有独立业务含义的分项。

组件以稳定业务 ID、类型和所属番号识别；OPTION 必须使用 `option_id`。缺失、重复、类型错误、归属错误或金额不一致均失败。即使不同分项互相抵消后总额碰巧一致，也不能通过。

## 参数界面

- 继续使用“系统回归 → 日本站”菜单。
- 每条用例展开后显示自己的参数输入控件。
- OPTION 使用可增删的表格行：名称、中文/日文名、计价类型、金额或比例、数量、是否自动计算。
- 多采购、上架数量、可入库数量、分批比例、交易号、退款目标金额等都使用普通输入框或选择框。
- 保持单选、当前筛选全选、全部用例全选和任意多选批量执行。
- 批量执行时，每条用例使用各自保存的参数，不共享上一条用例的临时修改。
- 批量执行默认串行。涉及同一客户余额、支付、退款或同一业务对象写入的用例禁止并行；只有目录显式声明 `parallel_safe=true` 的纯查询或完全隔离用例才允许并行。

- 规则名称和业务阶段。
- `execution_id`、批次 ID、用例 ID、执行账号。
- 订单号、问题产品 ID、采购记录 ID。
- 前置状态摘要。
- 尝试执行的动作和关键参数。
- 真实错误信息。

## 测试策略

### 单元测试

- 15 个 `guard_kind` 都映射到唯一阶段、前置构造器和目标动作。
- 缺少构造器时必须阻塞，不允许退回普通问题产品执行。
- 预期错误匹配、意外错误、成功未拦截、未知写状态和副作用检测。
- 相同错误出现在错误阶段时必须失败。
- 请求超时但查询确认实际已写入时继续验证，不重放写请求。
- 固定 OPTION、百分比 OPTION、其他费用和单番运费的变量构造。
- 费用分项缺失、重复、类型错误、金额不一致或互相抵消时失败。

### 集成测试

- 路由必须向 `GuardRunner` 注入规则执行服务，不再注入普通 `ProblemGoodsRunner.execute`。
- 单条、任意多选和全选都保留各用例独立参数。
- 大额退款普通账号无副作用拦截、部长账号续跑和真实余额入账形成同一个 `execution_id` 的复合结果。
- 服务重启后恢复 `waiting / account_required`，不重新造单或重放普通账号步骤。
- 最终一致性轮询能区分延迟写入、确认未写入和状态不确定。
- 两个批次的参数、订单、问题产品和证据相互隔离。
- 查询必须按执行 ID、批次号和业务 ID 唯一匹配，不能误命中历史数据。
- 旧系统回归和数据脚本接口返回结构保持兼容。

### 真实环境验证

1. 使用管理员账号 `admin` 和客户 `300001` 逐条执行可构造的拦截用例。
2. 核对每条通过记录都包含真实后端错误和前后状态证据。
3. 执行 `JP-PAY-009`、`JP-PAY-010`，确认订单详情中存在要求的 OPTION 和全部费用。
4. 批量执行全部 77 条；单条失败后继续。
5. 运行项目完整测试并重启服务。

## 验收标准

- 不再有任何拦截用例通过普通问题产品成功流程来判定。
- 15 条拦截用例分别显示真实规则阶段和参数。
- 可构造规则只有命中真实后端错误且无禁止副作用才通过。
- 环境或后端能力缺失明确显示为阻塞，不误报失败或通过。
