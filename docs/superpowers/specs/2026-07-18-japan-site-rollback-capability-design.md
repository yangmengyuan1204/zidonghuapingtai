# 日本站分支流程与回退能力设计

## 1. 背景

日本站当前已有购物车、订单、支付、采购、仓库、配送单、辅料、资金和问题产品等主要数据脚本，能够覆盖标准主流程及部分常用流程。下一阶段的目标不是收录真实日本站的全部接口，而是围绕测试所需的业务状态，补齐主流程上的分支、小流程和流程性回退能力，并让 DeepSeek 在受控条件下通过自然语言发现和编排这些能力。

本地现状盘点结果：

- “日本站测试”项目数据库中已有 63 条接口用例。
- 代码内置接口目录有 56 条，缺少移动端 4 条和国际物流配送 3 条。
- 日本站现有 18 个注册数据脚本。
- DeepSeek 当前开放 15 个受控工具，覆盖面小于现有脚本能力。
- 数据脚本代码还调用了辅料、充值、问题产品和订单附加选项等未完整登记的接口。
- 当前实时浏览器录制器能够捕获 XHR/fetch，但会原样保留请求头和请求体，存在密码、Cookie、Token 等敏感信息进入录制事件的风险。

因此，本设计采用“业务状态覆盖”而非“接口数量覆盖”作为建设标准，产出结构为：

```text
业务域 → 可造状态/异常状态 → 所需接口 → 现有脚本 → DeepSeek能力 → 缺口与优先级
```

## 2. 目标与非目标

### 2.1 目标

- 建立安全的真实站单动作录制模式，由用户操作、系统捕获并识别接口。
- 将流程性回退建模为严格相邻的状态边，禁止跨级回退。
- 首批覆盖订单 3 条回退边、配送单 3 条回退边和指定商品下架回核查中的能力。
- 将主流程上的查询型分支、状态内修改、异常数据构造和相邻回退统一纳入能力元数据。
- DeepSeek 只负责理解用户目标和编排已审核能力，后端负责合同编译、风险校验、执行和真实状态验证。
- 任一步失败时停止后续操作，保留最后一个已验证状态并支持续跑。
- 保持现有 18 个日本站脚本的函数签名、入参、返回值和主流程兼容。

### 2.2 非目标

- 不追求真实日本站全部接口的完整收录。
- 不允许 DeepSeek 自由猜测接口、参数、订单号、配送单号或商品 ID。
- 本期不支持跨越支付、退款、充值和其他资金状态的回退。
- 录制结果不直接自动回放，也不直接成为 DeepSeek 可用工具。
- 本期不新增数据库结构。
- 不重写或无关重构现有主流程脚本。

## 3. 总体架构

能力建设分为事实发现、受控实现和智能体开放三层：

```text
用户在真实日本站执行一个动作
  → 安全录制器捕获脱敏后的 XHR/fetch
  → 识别主变更接口、查询接口、动态参数和前后状态
  → 生成人工审核的能力草稿
  → 编写独立受控脚本与真实状态校验器
  → 自动化测试和低风险真实验收
  → 审核启用能力元数据
  → DeepSeek 按项目、模块和风险发现并编排
```

职责边界：

- 录制器：只发现真实请求事实，不决定业务能力是否安全。
- 能力草稿：描述接口、参数和状态变化，不具备直接执行权限。
- 数据脚本：实现确定性接口调用、幂等、错误处理和状态验证。
- 能力元数据：声明语义、参数、状态边、风险、执行器和校验器。
- DeepSeek：将自然语言转换为候选目标和操作序列。
- 后端合同编译器：验证对象来源、状态边、风险边界和执行顺序。

## 4. 安全录制模式

### 4.1 会话状态

录制会话采用以下状态：

1. `login_ready`：用户登录和导航阶段，不捕获业务请求。
2. `armed`：开始单动作检查点，清空此前事件并允许捕获。
3. `capturing`：用户只执行一个明确业务动作。
4. `frozen`：动作完成后停止捕获，冻结本次脱敏事件。
5. `reviewed`：用户和系统确认主接口、参数及状态变化。

一次检查点只允许对应一个业务动作。若捕获到多个可能的变更接口，结果标记为“识别歧义”，不得自动选择。

### 4.2 敏感数据处理

敏感信息必须在采集入口处理，禁止先保存原文再事后删除。

- 请求头使用白名单，仅保留 `Content-Type` 等结构信息。
- `Authorization`、`Cookie`、Token 类请求头永不进入录制事件。
- 请求体按字段名递归脱敏密码、验证码、认证凭据和个人信息。
- 响应体限制最大尺寸，只保留接口识别和状态验证所需字段。
- 响应体中的 Token、个人信息和账户凭据按同一规则递归脱敏。
- 日志、错误响应、能力草稿和测试断言均不得输出敏感原值。

### 4.3 接口识别

单动作录制完成后，系统生成只读预览：

- 主变更接口的 method、path 和请求字段结构。
- 动作前置查询、动作后结果查询及其用途。
- 动态参数及来源，例如订单号、配送单号、商品 ID。
- 推断的 `from_state` 和 `to_state`。
- 响应状态和用于判断业务成功的候选字段。

用户确认业务名称、对象、参数含义和状态变化后，才允许形成能力草稿。能力草稿仍为禁用状态，不能直接回放或对 DeepSeek 可见。

## 5. 回退状态模型

### 5.1 订单回退

订单只允许以下相邻回退：

```text
已报价 → 待报价 → 订单采购 → 订单翻译
```

对应 3 项独立能力：

1. 已报价回退到待报价。
2. 待报价回退到订单采购。
3. 订单采购回退到订单翻译。

从已报价回到订单翻译必须顺序执行三项能力，禁止调用跨级接口或跳过中间状态校验。

### 5.2 配送单回退

配送单只允许以下相邻回退：

```text
已报价 → 待报价 → 待装箱 → 待翻译
```

对应 3 项独立能力：

1. 已报价回退到待报价。
2. 待报价回退到待装箱。
3. 待装箱直接回退到待翻译。

待装箱回退到待翻译不包含撤销装箱完成、出货物或取消箱子等中间清理流程。

### 5.3 商品下架回退

指定的已上架商品通过负数数量操作回退到核查中。该能力与订单、配送单状态边分离，并强制要求：

- 明确指定商品对象，不能默认作用于全部商品。
- 负数数量符合真实接口规则。
- 执行前确认商品处于允许下架的状态。
- 执行后查询指定商品是否进入核查中。

## 6. 单步执行与多步编排

每条状态边的执行顺序固定为：

```text
读取真实当前状态
  → 校验对象和 from_state
  → 调用一条相邻回退接口
  → 查询真实结果
  → 校验 to_state
  → 记录脱敏审计事件
```

幂等规则：

- 对象已经处于目标状态时，不重复修改，返回幂等成功。
- 对象处于其他状态时，返回当前状态和允许的下一条相邻边。
- 不根据模糊响应文本推测成功，必须有真实状态查询证据。

多步规则：

- DeepSeek 可以理解“订单退回订单翻译”等目标，但后端必须编译成相邻步骤序列。
- 确认界面展示完整步骤、目标对象和风险提示。
- 用户一次确认完整合同后，执行器仍逐步校验。
- 任一步接口失败、状态未变化或查询异常时，立即停止后续步骤。
- 会话保存最后一个已验证状态，允许从原任务继续执行未完成步骤。

## 7. 主流程分支能力

主流程节点允许挂接以下类型的小分支：

- 查询型分支：读取当前对象、选项、费用或状态，不修改数据。
- 状态内修改：不推进主节点，但改变该节点内的业务属性。
- 异常数据构造：为测试生成边界值或异常状态。
- 相邻回退：沿已审核状态边逆向移动一步。

每项能力元数据至少包含：

- 稳定 key、中文名称、业务模块和适用项目。
- 自然语言意图、同义表达和正反示例。
- 必填参数、可选参数、默认值、类型和来源优先级。
- `from_state`、`to_state`、前置条件和幂等策略。
- 只读/写入属性、风险级别和确认策略。
- 所需账户角色和权限范围。
- 执行函数、结果校验器和智能体启用状态。

能力只有在接口事实确认、脚本实现、状态校验、自动化测试和人工审核全部通过后，才设置为智能体可见。

## 8. DeepSeek 接入

DeepSeek 只加载当前日本站项目、相关业务模块且已启用的能力元数据。运行流程：

1. 解析用户自然语言和对象标识。
2. 查询当前真实状态或生成只读预检操作。
3. 选择合法目标状态和候选能力。
4. 后端将目标编译为相邻操作序列。
5. 校验对象来源、状态边、账户权限和风险范围。
6. 向用户展示完整执行合同并等待确认。
7. 顺序执行能力并逐步验证。

不支持的请求必须明确报告能力缺口，不能隐藏在 assumptions 中，也不能让模型临时拼接接口。

## 9. 异常处理

- 多个变更接口：标记识别歧义，要求人工选择或重新单动作录制。
- 起点状态错误：执行前阻断，返回当前状态和允许的下一条边。
- HTTP 成功但状态未变化：判定业务失败。
- 多步任务中途失败：停止后续步骤，保留最后验证状态。
- 登录失效或会话超时：暂停录制或执行，由用户重新登录。
- 重复点击或重复执行：先查询状态，已到目标时不再次修改。
- 未知响应或缺少校验接口：能力保持禁用，不能以日志文本代替验证。
- 支付、退款和资金状态：本期报告超出能力范围，不执行回退。

## 10. 测试与验收

### 10.1 安全测试

- 请求头白名单测试。
- 请求体和响应体递归脱敏测试。
- 大响应截断和异常响应测试。
- 登录阶段不捕获测试。
- 断言密码、Cookie、Authorization、Token 和验证码不进入事件、日志或草稿。

### 10.2 状态图与脚本测试

7 条回退能力分别覆盖：

- 正确起点和成功终点。
- 起点状态不匹配。
- 接口调用失败。
- 接口成功但终点未变化。
- 已处于目标状态的幂等路径。
- 对象标识缺失或不一致。

状态图测试必须证明不存在跨级边，并且多步编排只生成相邻步骤。

### 10.3 智能体合同测试

- “已报价订单退回订单翻译”编译为 3 条订单相邻边。
- “配送单退回待翻译”按当前状态编译为所需相邻边。
- 未提供对象且无法从上下文确定时必须澄清。
- 支付、退款和资金回退请求必须被拒绝或报告能力缺口。
- DeepSeek 不得编造订单号、配送单号、商品 ID 或状态。

### 10.4 低风险真实验收

- 使用专用测试数据逐条验证回退边。
- 每次只执行一条边并记录真实前后状态。
- 真实逐边验证全部通过后，再验证一次多步编排。
- 不批量执行，不使用生产业务数据，不跨越支付或资金状态。

## 11. 分阶段实施范围

### 阶段 1：安全录制器

预计核心文件：

- 修改 `app/services/browser_session.py`：增加录制状态、入口脱敏、事件清空/冻结和安全预览。
- 修改 `app/routers/browser_record.py`：增加开始检查点、停止检查点和识别预览接口。
- 新增独立测试文件：覆盖脱敏、录制状态和路由合同。

本阶段不改数据库结构，不保存原始认证信息。

### 阶段 2：录制回退接口事实

用户逐条操作 7 个回退动作，系统形成脱敏能力草稿。每条草稿记录接口、参数结构、前后状态和验证证据，但保持禁用，不直接回放。

### 阶段 3：独立回退脚本

预计核心文件：

- 新增 `app/data_scripts/rollback.py`：只承载日本站回退业务，不修改其他数据脚本逻辑。
- 扩展现有脚本注册或能力元数据：登记回退入口、状态边、风险和验证器。
- 新增独立测试文件：覆盖 7 条边、幂等、停止和续跑。

现有脚本的函数签名、注册 key、入参和返回值保持不变。

### 阶段 4：DeepSeek 接入

预计修改智能体工具、合同编译和对应测试，使 DeepSeek 只能看到已审核的日本站回退能力，并将跨节点目标编译为相邻步骤。

每个阶段开始前重新检查工作区，只修改当期相关文件；若实际需要超过 2 个核心文件，先说明原因和文件用途并等待确认。

## 12. 验收标准

- 敏感凭据不进入录制事件、日志、数据库或能力草稿。
- 7 条回退边均有明确接口事实、参数合同和真实状态校验器。
- 订单和配送单不允许跨级回退。
- 指定商品负数下架只作用于确认的商品对象。
- 任一步失败时后续步骤不会执行，任务可从最后验证状态继续。
- 现有 18 个日本站脚本不受影响。
- 只有测试通过并人工审核的能力才对 DeepSeek 可见。
- 自动化测试通过后，低风险真实逐边验收通过。
