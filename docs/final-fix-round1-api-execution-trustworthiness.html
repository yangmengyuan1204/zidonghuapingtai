3. 根因

  • parse_json_value(case.assert_rule, {}) 将断言 JSON 解析失败静默降级为 {}。
  • 通用模板渲染器把已识别但缺失的变量替换为空字符串，执行器没有渲染前或渲染后预检。
  • 没有断言检查项时使用 200 <= status_code < 400 兜底，混淆“无断言”和“断言通过”。
  • contains 缺失变量可变为空字符串；int() 可截断浮点状态码。这两个边界同样能造成结果不可信。
  • Python json.loads 默认接受 JSON 标准禁止的 NaN/Infinity；Unicode isdigit() 与 int() 的接受集合不一致，均可绕过请求前预检。

4. 空断言产品语义核对

Vue3 新建 ApiCase 默认显式配置 status_code: 200；bootstrap 生成的内置用例也显式配置状态码。没有找到“空断言等价于仅检查 HTTP 状态”的产品说明或历史测试。

正式数据库只读统计：ApiCase 共 1,881 条；未配置断言 0 条；空对象断言 0 条；显式 status_code 1,881 条；显式 contains 3 条。因此本轮把空/缺失断言视为配置错误，不会阻断现有正式 ApiCase。

13. 是否彻底消除假成功

在本轮审查范围和当前执行器支持的断言类型（status_code、contains）内：是。

  • 断言配置损坏（包括 NaN/Infinity）、缺失、为空或没有有效检查项时，不能再凭 2xx/3xx 通过。
  • 请求和 contains 中所有闭合的双花括号占位符会在渲染前检查；变量值引入的残留会在渲染后再次检查。
  • 所有配置错误均在 HTTP 请求前失败，并进入 Records/日志/返回结果。
  • 合法断言通过仍为 passed，合法断言失败仍为 failed，合法变量替换、批量提取和重跑保持正常。

未发现当前受支持路径中仍可稳定产生假成功的已知入口。该结论不扩展到未来新增但尚未实现的断言类型，也不把“用户明确只配置 contains、且 contains 实际匹配”误判为假成功。
