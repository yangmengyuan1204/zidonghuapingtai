2. 已完成的功能范围

模块与菜单

  • 新增独立菜单“系统回归”。
  • 按项目分类，首期实现日本站。
  • 支持分类查看、单条执行、当前分类选择、批量执行和全选/取消。
  • 批量默认串行，未声明 parallel_safe=true 的用例不并发。

参数输入

  • 全部使用普通输入框、数字框和下拉框，不要求填写 JSON。
  • 支持单番数量、商品数量、报价单价、中国国内运费。
  • 支持其他费用金额与其他费用名义。
  • 支持按单番新增、删除 OPTION，并填写计价方式、价格/比例和数量。
  • 问题类型显示文字，提交时保留后端数字值。

批次执行

  • 每次执行生成独立 execution_id 和批次号。
  • 执行瞬间冻结每条用例参数，页面后续修改只影响下一批次。
  • 单条失败后继续执行后续用例。
  • 每条用例保留独立订单、问题产品和采购记录证据。

结果证据

  • 记录预期阶段、实际阶段、执行账号、响应证据和业务差异。
  • 区分 required、forbidden、allowed、unclassified effects。
  • 前端可查看结构化证据，不只显示成功或失败。
  • 未分类业务变化不允许通过。

3. 金额与费用对账规则

  1. 支付实际金额只取客户余额真实扣款，或已匹配且完成财务确认的银行流水。
  2. 问题产品退款实际金额只取客户余额真实入账；不设计银行退款证据。
  3. 禁止使用支付请求参数或本地计算结果冒充实际金额。
  4. 人民币按对应报价/支付证据汇率换算日元，日元最终总额使用四舍五入整数。
  5. 误差不超过 1 日元通过，达到 2 日元失败。
  6. 支付必须为出账，退款必须为入账；方向错误直接失败。
  7. 仅接受能与订单号、配送单号、问题产品 ID、采购记录或银行流水唯一匹配的记录。
  8. 缺失流水、历史误命中、重复歧义、缺少汇率、方向错误均失败。

百分比 OPTION 公式

OPTION 金额(CNY) = OPTION 比例 ÷ 100 × OPTION 数量 × 商品单价(CNY)
CNY 精度         = 0.01，ROUND_HALF_UP
JPY 换算         = 所有 CNY 分项求和后 × 对应汇率，再 ROUND_HALF_UP 到整数
身份识别         = option_id；名称只用于展示
允许误差         = 1 JPY

防止总额碰巧相等

费用合同分别声明 required_components、optional_components、forbidden_components 和 system_generated_components。分项缺失、重复、类型错误、OPTION ID 错误或金额错误均失败，即使最终总额相同也不能通过。

4. 执行状态、错误归类和恢复机制

项目规则
统一结构状态passed、failed、blocked、waiting。
旧接口兼容状态旧顶层字段和 waiting_account 行为继续保留，新增标准状态放在结构化结果中。
环境前置不足blocked / precondition_capability_missing。
目标接口不可调用blocked / target_action_unavailable。
后端规则缺失真实目标接口调用成功但未拦截：failed / backend_guard_missing。
阶段错误相同错误发生在错误阶段：failed / unexpected_guard_stage。
写请求超时区分 confirmed_written、confirmed_not_written、indeterminate。
未知写状态blocked / unknown_write_state，禁止自动重试。
服务重启恢复 execution state；不重新造单，不重放可能已成功的写动作。
最终一致性关键状态与客户账单使用轮询确认，不以单次即时查询作为最终证据。

错误匹配优先级

业务错误码 → 结构化错误字段 → HTTP 状态 → 错误文案正则。同时记录 expected_stage 和 actual_stage，前置构造阶段提前失败不能冒充目标规则通过。

5. 大额退款复合场景

  1. 普通账号对真实问题产品执行采购处理。
  2. 必须命中退款达到或超过 500 元的部长权限拦截。
  3. 拦截后复核问题产品状态和客户余额，普通账号步骤不得产生退款或余额变化。
  4. 优先读取项目内“沈文妮”部长账号；自动登录失败时进入等待账号状态。
  5. 用户手工输入账号密码后，从同一订单、同一问题产品、同一采购阶段继续。
  6. 部长步骤成功后，必须查询唯一客户余额入账记录，且方向为 credit。
  7. 账号等待和恢复信息持久化；密码只在内存中使用，不写入数据库或响应。
该场景已实现并完成自动化测试，但尚未在当前真实日本站环境进行完整人工验收。

12. 尚未完成和验收前置条件

当前不能称为“所有开发测试完毕”的原因：
  1. 修订后的 77 条用例尚未在真实日本站环境逐条全量执行。
  2. 转寄订单、待财务付款、未付尾款、已上架数量、同番多采购等特殊状态依赖真实环境前置能力。
  3. 大额退款复合流程已完成自动化验证，但尚需普通账号和真实部长账号完成一次端到端业务验收。
  4. 银行支付需要真实银行流水匹配和财务确认，必须在具备该流程的测试环境验证。
  5. 项目全量测试仍有一个与本次无关的 favicon 路由基线失败，需要对应 Frontend V2 任务处理。

达到“全部完成”的建议判定条件

  1. 在指定日本站测试环境串行运行 77 条用例。
  2. 对所有 failed/blocked 逐条确认：真实后端缺陷、环境前置不足或脚本问题。
  3. 至少完成一次大额退款普通账号拦截和部长账号同对象继续。
  4. 确认余额、银行流水、问题产品状态与费用分项证据均可追溯。
  5. 修复或重新确认 favicon 路由基线后，再运行一次项目全量测试。
  6. 真实业务负责人确认生成订单和账单结果后，状态方可更新为“全部开发测试完成”。
